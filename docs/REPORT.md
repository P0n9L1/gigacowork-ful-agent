## 0. Коротко

Собран агент, который по трём выгрузкам Excel (ФУЛ из 1С, реестр Cloud,
сотрудники 1С) выпускает готовый файл: новые строки реестра Cloud по форме
из 12 колонок, повторные отправки, возможные пропуски, список «Требует
внимания» и журнал обоснований по каждому ФУЛ.

Все решения о статусе ФУЛ, группе и логисте принимает детерминированный
скрипт навыка на Python. Модель запускает скрипт и пересказывает результат —
поэтому нет выдуманных значений и результат воспроизводим.

**Инструмент и модель:** GigaChat API, модель `GigaChat-2-Max`
(scope `GIGACHAT_API_PERS`). Harness минимальный — по варианту, разрешённому
в ТЗ: `tests/gigachat_run.py` запускает скрипт навыка, отдаёт модели системный
промпт и сводку скрипта, модель формулирует ответ пользователю. Дополнительно
агент прогнан в harness Hermes Agent (Nous Research) на пустом сообщении
с тремя приложенными файлами — содержимое результата совпало. SKILL.md, скрипт
и системный промпт от harness не зависят и переносятся в GigaCowork без
изменений: решения принимает скрипт, модель влияет только на текст ответа.

## 1. Вопросы заказчику

В описании процесса правило либо неоднозначно, либо не описано. По каждому
вопросу указано, кому он адресован, зачем нужен ответ и какое допущение
принято до ответа (оно реализовано в агенте и помечено в коде/правилах).

| № | Кому | Вопрос | Зачем | Принятое допущение |
| --- | --- | --- | --- | --- |
| 1 | Руководитель логистики | Если предпочтительный логист поставщика в отпуске или уволен, брать второго по истории с этим поставщиком или наименее загруженного в группе? | От этого зависит, кто получит заказ в самый частый проблемный момент — подмену на время отпуска | Берём наименее загруженного в группе, как написано в БТ; второй по истории не выбирается |
| 2 | Руководитель логистики | Правило «один поставщик в пачке — один логист» конфликтует с правилом групп, если у одного поставщика в пачке есть и air-, и sea-заказ из Китая. Что главнее? | Иначе агент либо нарушит группу, либо правило единства логиста | Группа считается по каждому заказу; конфликт выносится в «Требует внимания», решения автоматом не принимаются |
| 3 | Сотрудник распределения | «Возможный пропуск» — это только сигнал или сразу подготовленная строка Cloud? | Определяет, сколько строк сотрудник проверит вручную | Строка формируется (заказ реально новый), ФУЛ дополнительно попадает в «Возможные пропуски» и «Требует внимания» с пометкой в комментарии |
| 4 | Сотрудник распределения | Загрузка считается по всем заказам «в работе» группы или только по заказам этого поставщика? | Влияет на выбор «наименее загруженного» | По всем заказам «в работе» соответствующей группы; назначения внутри текущей пачки тоже увеличивают загрузку |
| 5 | Руководитель логистики | История работы с поставщиком — за какой период? Учитываются ли старые закрытые заказы (confirm) и заказы годичной давности? | Старые заказы могут «перевесить» актуальную практику | Учитываются все записи реестра Cloud без ограничения по дате, любой статус; при равенстве — более свежая дата получения УЛ |
| 6 | Сотрудник распределения | Дубль внутри пачки: какой ФУЛ считать основным, если по заказу пришло два листа? | От этого зависит, чья дата, cut-off и номер ФУЛ попадут в Cloud | Основной — первый по дате и номеру ФУЛ; остальные помечаются как дубль, строк не создают |
| 7 | Сотрудник распределения | Если короткое имя в Cloud подходит к двум сотрудникам («Иванов А.» — двое), как поступать? | Неверное сопоставление искажает и историю, и загрузку | Не сопоставляем: имя остаётся как в Cloud, ФУЛ с таким логистом требует ручной проверки |
| 8 | Сотрудник распределения | Статус новой строки всегда «в работе»? Поля «Дата подтверждения» и «Документы получены» оставляем пустыми? | Форма реестра должна заполняться однозначно | Статус «в работе», оба поля пустые: событий ещё не было, подставлять дату нельзя |
| 9 | Руководитель логистики | Если способ доставки не указан, но страна — Китай, можно ли считать заказ «не air» и отдать в ВЭД? | Один из самых частых дефектов выгрузки | Нельзя: без способа доставки группа не определяется, строка не создаётся, ФУЛ идёт в «Требует внимания» |
| 10 | Сотрудник распределения | Нужно ли приводить способ доставки и страну к единому написанию (`Air` → `air`, `China` → `Китай`) или переносить как в 1С? | От этого зависит однородность реестра и будущие сводки | Приводим к канону из справочника; справочник открыт для правок (`references/dictionaries.md`) |

## 2. Алгоритм распределения

### 2.1. Последовательность шагов

```
1. Прочитать три книги Excel.
   Для каждой книги: перебрать листы, найти строку заголовков, сопоставить
   колонки по названию (синонимы), а не по номеру. Роль файла (ФУЛ / Cloud /
   сотрудники) определяется по набору найденных заголовков.
2. Нормализовать данные: даты, способ доставки, страну, поставщика
   (регистр, кавычки, дефисы, орг-форма), номер заказа (S0001234).
3. Построить контекст Cloud: множество заказов, загрузку логистов
   («в работе»), историю «поставщик → логист», последнюю дату получения УЛ.
4. Построить справочник сотрудников: ФИО, состояние, должность → группа.
5. Обработать ФУЛ в порядке (дата ФУЛ, номер ФУЛ):
   a. нет номера заказа            → ошибка данных, строку не создавать;
   b. заказ уже был в этой пачке   → дубль в пачке, строку не создавать;
   c. заказ есть в Cloud           → повторная отправка, комментарий в Cloud;
   d. нет способа доставки/страны  → не определено, строку не создавать;
   e. определить группу по air/стране;
   f. если поставщик уже распределён в пачке — взять его логиста;
      иначе выбрать логиста (история → иначе наименее загруженный);
   g. если в группе нет доступных — логист «не определено», строка создаётся;
   h. проверить возможный пропуск (дата ФУЛ раньше последней записи Cloud);
   i. записать строку, журнал, при необходимости — «Требует внимания».
6. Сохранить result.xlsx и вывести короткую сводку.
```

### 2.2. Таблица решений

| Условие | Статус | Строка Cloud | Логист | «Требует внимания» |
| --- | --- | --- | --- | --- |
| нет номера заказа в комментарии | ошибка данных | нет | — | да |
| заказ второй раз в пачке | дубль в пачке | нет | — | да |
| заказ уже есть в Cloud | повторная отправка | нет (комментарий в существующую) | из Cloud | нет |
| нет способа доставки | ошибка данных | нет | — | да |
| не air и нет страны | ошибка данных | нет | — | да |
| air, страны нет | новый заказ | да, страна «не определено» | по правилам | да |
| новый поставщик | новый заказ | да | наименее загруженный в группе | нет |
| поставщик уже в пачке | новый заказ | да | логист этого поставщика | нет |
| предпочтительный логист в отпуске/уволен | новый заказ | да | наименее загруженный | нет |
| в группе все недоступны | новый заказ | да | `не определено` | да |
| ФУЛ раньше последней записи Cloud | новый заказ + пропуск | да | по правилам | да |
| заказы поставщика в разных группах | новый заказ | да | по правилам группы | да |

### 2.3. Выбор логиста (псевдокод)

```python
def pick_logist(group, supplier, cloud, staff, load):
    candidates = [e for e in staff if e.group == group and e.available]
    if not candidates:
        return "не определено", "нет доступных логистов в группе"

    # 1. история работы с поставщиком (любой статус заказа)
    hist = counter(order.logist for order in cloud if order.supplier == supplier)
    top, count = max(hist, key=(count, last_ul_date, -load, name))
    if top in candidates:
        return top, f"чаще всех работал с поставщиком: {count} заказов"

    # 2. предпочтительный недоступен — наименее загруженный
    return min(candidates, key=(load, name)), "наименее загружен; <причина пропуска предпочтительного>"
```

Ключевые детали, которые проверяются тестами:

- приоритет `air` над страной: air-заказ из Гонконга идёт в авиаперевозки,
  а не в ВЭД;
- Гонконг/Макао/CN/КНР/China считаются Китаем;
- наименее загруженный выбирается **после** исключения отпусков, уволенных,
  ассистентов и руководителей;
- один поставщик в пачке — один логист, даже если его загрузка выросла;
- тай-брейки: свежесть истории → меньшая загрузка → ФИО по алфавиту
  (нужны для воспроизводимости).

### 2.4. Сложные случаи и что делает агент

| Случай | Поведение агента |
| --- | --- |
| Повторная отправка ФУЛ | новой строки нет; готовый комментарий «Повторная отправка ФУЛа, 06.11.2026» (дата ФУЛ) в листе «Повторные отправки» |
| Дубль внутри пачки | второй ФУЛ по тому же заказу — без строки, с пояснением, какой ФУЛ основной |
| Новый поставщик | истории нет → наименее загруженный в группе, обоснование фиксируется |
| Предпочтительный логист в отпуске | наименее загруженный в группе; в обосновании указано, кто был предпочтителен и почему пропущен |
| Предпочтительный уволен | то же; уволенный не рассматривается как кандидат |
| Все сотрудники группы недоступны | строка создаётся, логист `не определено`, заказ в другую группу не передаётся |
| Нет номера заказа | строка не создаётся, значение не выдумывается |
| Нет способа доставки | группа `не определено`, строка не создаётся |
| Нет страны при air | группа определяется, страна `не определено`, ФУЛ в «Требует внимания» |
| Нет страны при sea/truck | группа `не определено`, строка не создаётся |
| ФУЛ раньше последней записи Cloud | возможный пропуск: строка + флаг + отдельный лист |
| Поставщик записан по-разному | сравнение без регистра, кавычек, дефисов, пробелов и орг-формы |

## 3. Принятые допущения

| № | Допущение | Почему |
| --- | --- | --- |
| 1 | «Повторная отправка» определяется по наличию номера заказа в Cloud, даже если статус `confirm` | Заказ уже в реестре — дубль создавать нельзя, статус не важен |
| 2 | Дата в комментарии повторной отправки — дата ФУЛ, формат `ДД.ММ.ГГГГ` | В БТ формат не задан, дата ФУЛ — единственная однозначная дата события |
| 3 | Строка Cloud для возможного пропуска создаётся с пометкой в комментарии | Заказ новый; сигнал нужен, чтобы сотрудник проверил, но данные уже готовы |
| 4 | Статус новой строки — «в работе»; «Дата подтверждения» и «Документы получены» пустые | Новый заказ ещё не подтверждён и документы не получены |
| 5 | Логист пишется коротким именем, как в Cloud (`Кузнецов Д.С.`), для нового сотрудника — полное ФИО | Однородность реестра; в Cloud уже так |
| 6 | Загрузка = число заказов «в работе» в группе, включая назначенные в текущей пачке | Ближе к реальной загрузке на момент следующего заказа |
| 7 | История с поставщиком — все заказы Cloud, без ограничения по дате | Ограничение периода в БТ не задано; вынесено в вопросы (№5) |
| 8 | Названия поставщиков сравниваются без орг-формы и пунктуации | В выгрузках один поставщик встречается в 3–4 написаниях |
| 9 | При неоднозначном коротком имени сотрудник не сопоставляется | Лучше не считать историю, чем приписать её не тому человеку |
| 10 | Неизвестное состояние сотрудника (не «Работает», не отпуск, не уволен) считается недоступным с причиной | Безопасное поведение: не назначать того, чей статус неясен |
| 11 | Конфликт «один поставщик — один логист» с разными группами не разрешается автоматически | Требуется решение человека, БТ этого не описывает |
| 12 | Страна и способ доставки приводятся к канону (`China` → `Китай`, `Air` → `air`) | Единый вид реестра и корректное сравнение |

### 4.2. Как проверялся эталон

Эталон заполнен вручную по правилам из БТ, затем сверен построчно с
результатом агента: назначения, группы и комментарии разобраны по каждому
ФУЛ (см. лист «Журнал решений» и приложение А). Расхождения первого прогона
были разобраны: три из них оказались ошибками эталона (например, загрузка
Иванова была 3, а не 2, из-за заказа `S0001008` в статусе «в работе»),
остальные — дефектами скрипта (ложный номер заказа из текста «уточняется»,
дубли в «Требует внимания», полные ФИО вместо коротких). После правок
результат совпал с эталоном по всем 24 ФУЛ.

## 7. Что доработал бы дальше

1. **Реальные данные заказчика.** Проверить на 5–10 реальных пачках и сверить
   с решениями сотрудника: это единственный способ поймать правила, которых
   нет в БТ (например, «не назначать одного логиста на двух крупных
   поставщиков»).
2. **Настраиваемые правила вместо констант.** Вынести приоритеты
   (история/загрузка/свежесть), список стран Китая и порог «старой» истории
   в YAML-справочник, чтобы заказчик менял их без правки кода.
3. **Учёт веса и объёма заказа.** Загрузка по числу заказов не равна нагрузке:
   если в Cloud появится вес/объём, считать загрузку по ним.
4. **Отдельный лист «что изменится в Cloud».** Diff-режим: агент показывает
   не только новые строки, но и предлагаемые изменения комментариев
   у повторных отправок — удобнее переносить вручную.
5. **Проверка на дубли поставщиков-юрлиц.** Транслитерации («Деним Хаус» /
   «Denim House») сейчас не склеиваются: нужен управляемый словарь алиасов
   поставщиков.
6. **Расширение на второй кейс** из БТ — сверка упаковочного листа с заказом
   и одно письмо менеджеру со всеми отклонениями: механика та же
   (файлы → правила → готовый результат).

## 8. Мотивация участия

**1) Почему интересен проект.** Это ровно тот класс задач, где автоматизация
даёт измеримый эффект: 65 ФУЛ вручную, цепочка «тип перевозки → группа →
поставщик → доступность → загрузка» и ошибки, которые всплывают поздно.
Мне интересно сделать не «чат с моделью», а предсказуемый инструмент, где
решение принимает правило, а модель объясняет результат человеку — так же,
как сделано в этом тестовом.

**2) Роль в команде.** Инженерная: разбирать правила заказчика в алгоритм,
писать и тестировать скрипты навыка, строить синтетику с ловушками и метрики
приёмки, доводить агента до состояния «загрузили и работает». Готов
и общаться с заказчиком по неоднозначным местам — список вопросов выше как
пример.

**3) Время.** 15–20 часов в неделю, готова длительная работа (6+ месяцев),
совмещаю с учёбой в РЭУ (2-й курс, «Цифровые технологии»).
